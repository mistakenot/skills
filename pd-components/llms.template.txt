# pd-components v{{VERSION}}

> Light-DOM web components for rich single-file HTML planning documents.
> One classic script tag, no build step, works from file:// pages. The HTML
> source is the canonical data — write it like markup, the components render
> it into an interactive doc.

Current release: `{{TAG}}`. Pin every generated doc to this exact tag (jsDelivr
caches tags immutably, so old docs never change appearance under the reader).

## Boilerplate

Every doc starts with exactly this head. Use a CLASSIC script tag (not
type="module" — module scripts are CORS-blocked when the file is opened via
file://).

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>NNN: Doc title</title>
  <script src="https://cdn.jsdelivr.net/npm/@tailwindcss/browser@4"></script>
  <script src="{{CDN_BASE}}/pd.min.js" defer></script>
</head>
<body>
  <!-- AI: When a PR is created for this work, update pr="pending" below with the PR URL -->
  <pd-doc title="NNN: Doc title" status="draft" pr="pending" generated="YYYY-MM-DD">
    ...
  </pd-doc>
</body>
</html>
```

Tailwind is optional — include it only if the doc has freeform/wireframe
content. pd-* components style themselves.

## Authoring rules

- **Use `<md>` for prose content** (paragraphs, lists, links, inline code,
  tables). Agents read and generate markdown natively at lower token cost than
  HTML. Reserve raw HTML for pd-* structural elements and Tailwind wireframe
  layouts.
- Structure lives in pd-* elements and ids, never in utility-class div soup.
  Tailwind classes belong ONLY inside freeform/wireframe content.
- Give every pd-section a stable, kebab-case id. Threads and deep links anchor
  to these ids; content can then be freely rewritten without orphaning its
  discussion.
- **Prefer structured attributes over prose.** Anything a reader would scan,
  count, or cross-reference — phase order, file changes, coverage, dependencies
  — belongs in attributes, not sentences. The components derive visual summaries
  (pd-scope, pd-dag, pd-trace), cross-highlighting, and consistency checks from
  those attributes for free. Keep prose for the *why*; put the *what* in markup.
- **Visual-first sections.** Open a section with its diagram/graph/matrix, then
  put the explanation in a `summary=` (auto-collapsed) or `<pd-collapse>`. Don't
  describe in prose what an attribute-driven component already shows.
- Content is edited in place; threads are APPEND-ONLY. Never delete or rewrite
  an existing pd-comment — append a new one and update the thread's status
  attribute. Resolved threads collapse automatically in the UI; the history
  stays in the file.
- Place a pd-thread in the source directly after the element it discusses, and
  set anchor to that element's id (or a pd-file's path).
- doc status attribute: draft | in-review | approved.

## Components

### <pd-doc title status pr generated>
Document shell: header, PR link bar, tab navigation (when it contains pd-tab
children), floating "Copy for agent" bar for pending comments, provenance footer.
Direct children: either pd-tab elements, or sections directly.

pr: "pending" shows a muted placeholder; a URL (e.g.
"https://github.com/org/repo/pull/42") renders a clickable badge. Omit entirely
if no PR tracking is needed. When the executor opens a PR, it should update
pr="pending" to the actual URL.

### <pd-tab name>
One page of a tabbed doc. Tab buttons show a badge with the count of open
threads inside. Deep links: #tab:Name, or any #element-id inside the tab.

```html
<pd-tab name="Solution"> ...sections... </pd-tab>
```

Tab roles (a deliberate audience split — follow it):
- **Solution = the end state** once the work is done. Human-consumed: someone
  checking the final outcome. The file-change tree (pd-files), API outlines,
  and final code snippets belong here.
- **Plan = the recipe** to get there. Agent-consumed: planning/executing. Keep
  it self-sufficient (pd-phase already lists its files inline).

### <pd-section id title summary>
Titled section with anchor link and a "+ comment" button (reviewers queue
comments in the browser). Body is `<md>` blocks and pd-* elements.

summary: optional one-line scan summary. When present, the summary shows
always-visible and the section body collapses into a "Details" disclosure
(add `open` to expand by default). The full body stays in the DOM for agents —
this is the human skim layer, not a content cut. Use it on prose-heavy sections.

```html
<pd-section id="approach" title="Approach">
  <md><script type="text/plain">
Token-bucket limiter as gateway middleware, backed by Redis.
Bursts up to bucket size are allowed; sustained rate is capped at the refill rate.
  </script></md>
</pd-section>
```

### <md>
Client-side markdown block. Use for prose content inside pd-* containers —
paragraphs, lists, inline code, links, tables. Replaces verbose HTML (`<p>`,
`<ul><li>`, `<code>`, `<a href>`) with compact markdown, rendered by marked
(loaded from CDN on demand — no extra script tag needed).

Use `<md>` for: section bodies, phase descriptions, AC criteria, notes —
anything that would otherwise be `<p>`, `<ul>`, `<table>`, `<a>`, or inline
`<code>`.

Keep raw HTML for: pd-* components (pd-mermaid, pd-code, pd-files, etc.),
wireframe layouts (Tailwind), content requiring HTML attributes.

**Always wrap `<md>` content in `<script type="text/plain">`** to prevent the
browser's HTML parser from interpreting angle brackets as tags. Without the
wrapper, markdown containing `<textarea>`, `<script>`, `<style>`, or any HTML
tag name in backtick-code will break the document structure — the parser treats
them as real HTML elements before marked ever runs.

```html
<pd-section id="limits" title="Rate limits">
  <md><script type="text/plain">
Per-client rate limiting at the gateway, backed by Redis:

- **Free plan**: 100 req/min
- **Partner plan**: 1000 req/min
- Exceeding the limit returns `429` with a `Retry-After` header
- Custom props via a `<textarea>` JSON editor

See the [design doc](https://example.com/design) for background.
  </script></md>
</pd-section>
```

### <pd-thread anchor status title priority> / <pd-comment by>
Append-only review thread. status: unresolved (default) | resolved | rejected.
priority: p1 (blocking) | p2 (important) | p3 (minor). by: review | author |
a person's name. Open threads render a reply box; closed ones collapse.

```html
<pd-thread anchor="approach" status="resolved" priority="p2" title="Why not sliding window?">
  <pd-comment by="review">Token bucket allows bursts — is that acceptable for the API tier?</pd-comment>
  <pd-comment by="author">Yes — bursts up to bucket size are within SLA; documented in the Approach section.</pd-comment>
</pd-thread>
```

### <pd-files> / <pd-file path change>
File-change list. Write flat pd-file children (cheap to append); renders as a
collapsible tree with +/~/− markers, per-file notes, and open-thread badges
for threads whose anchor equals the file path. change: add | edit | delete.

```html
<pd-files>
  <pd-file path="src/gateway/limiter.ts" change="add">Token bucket implementation</pd-file>
  <pd-file path="src/gateway/index.ts" change="edit">Wire limiter into request pipeline</pd-file>
  <pd-file path="src/legacy/throttle.ts" change="delete">Superseded</pd-file>
</pd-files>
```

### <pd-stepper> / <pd-phase n title files status depends-on>
Clickable, non-linear plan walkthrough. Selecting a phase shows its body and
highlights its files (comma-separated paths matching pd-file paths) in every
pd-files on the page. status: done | active | todo. Arrow keys navigate.

depends-on: comma-separated phase numbers this phase must follow. Drives the
pd-dag graph and conflict detection. Set it whenever an ordering actually
exists — it's the structured data the graph and the linter read.

Selection is shared: clicking a phase here, clicking its node in pd-dag, or
keyboard-focusing that node all select the same phase everywhere (stepper, dag,
and the file tree highlight stay in sync). No wiring needed — it's automatic.

```html
<pd-stepper>
  <pd-phase n="1" title="Limiter core" files="src/gateway/limiter.ts" status="done">
    <md><script type="text/plain">Implement and unit-test the bucket…</script></md>
  </pd-phase>
  <pd-phase n="2" title="Gateway wiring" files="src/gateway/index.ts" status="active" depends-on="1">
    <md><script type="text/plain">Apply per-route config…</script></md>
  </pd-phase>
</pd-stepper>
```

### <pd-mermaid caption>
Renders mermaid source (bundled beautiful-mermaid — no extra fetch, follows
light/dark mode). Supported types: flowchart/graph, sequenceDiagram,
stateDiagram(-v2), classDiagram, erDiagram, xychart-beta. Do NOT use other
types (gantt, pie, mindmap…) — they fall back to a source-code block. Put the
mermaid source as plain text content; indentation is fine.

```html
<pd-mermaid caption="Request path">
flowchart LR
  C[Client] --> G[Gateway] --> S[Service]
</pd-mermaid>
```

### <pd-code lang path lines highlight caption>
Syntax-highlighted snippet (highlight.js bundled — no extra fetch). lang:
go|ts|js|python|json|bash|yaml|sql|rust|diff (others auto-detect). path: shows
a filename header + copy button. lines: boolean, adds line numbers. highlight:
emphasize line ranges, e.g. "2-3,7". Put the code as the element's text
content. If the code contains <, >, or &, wrap it in a nested
<script type="text/plain"> to avoid HTML-escaping.

```html
<pd-code lang="go" path="internal/events/log.go" lines highlight="3-4" caption="Append under flock">
func AppendEvent(dir string, ev Event) error {
	f, _ := os.OpenFile(shard(dir), os.O_RDWR|os.O_CREATE, 0o644)
	flock(f, LOCK_EX)
	ev.Seq = lastSeq(f) + 1
	return writeLine(f, ev)
}
</pd-code>
```

### <pd-api kind name lang path caption> / <pd-member kind sig>
Token-efficient outline of a code symbol — the public surface only
(signatures + doc comments, no bodies). Generic by design: `kind` on the
container (class|struct|interface|module|enum|routes|schema|…) and on each
member (constructor|method|field|…) are free-form labels rendered as badges,
so the same component outlines a Go struct, a TS class, a REST route table, or
a SQL schema. Member signature goes in the `sig` attribute; the doc comment is
the member's text content. Signatures are syntax-highlighted with `lang`.
Prefer this over a full pd-code dump when the reader only needs the API shape.

```html
<pd-api kind="struct" name="loop.Service" lang="go" path="internal/loop/service.go" caption="Agent-facing state machine">
  <pd-member kind="constructor" sig="NewService(log *events.Log, pb *rules.Playbook) *Service">Binds the loop to the canonical log and folded snapshot.</pd-member>
  <pd-member kind="method" sig="Retrieve(intent string, domains []string, limit int) ([]Predicate, error)">Match + mint rt-ids; append one retrieval event; predicates only.</pd-member>
  <pd-member kind="field" sig="Lookback time.Duration">No-session gate fallback window (default 24h).</pd-member>
</pd-api>
```

### <pd-ac id title phases tests>
Acceptance-criteria card with traceability chips. phases: comma-separated
phase numbers covering it; tests: comma-separated test files.

```html
<pd-ac id="AC-1" title="Requests over the limit get 429" phases="1,2" tests="e2e/rate-limit.spec.ts">
  <md><script type="text/plain">
- Given a client at its request budget
- When it sends one more request within the window
- Then the gateway responds `429` with a `Retry-After` header
  </script></md>
</pd-ac>
```

### <pd-scope>
At-a-glance summary strip, fully derived — no attributes, no authoring. Counts
the pd-phase / pd-file / pd-ac / pd-thread elements already in the doc and
renders tiles: phase count + done/active/todo progress bar, file count + add/
edit/delete tally, criteria count + coverage gaps, open-thread count. Drop one
at the top of the first tab for an instant scan-level summary.

```html
<pd-scope></pd-scope>
```

### <pd-dag caption>
Phase dependency graph, fully derived from the pd-phase elements — no
attributes besides an optional caption. Reads depends-on for explicit edges and
auto-detects conflict edges (two phases share a file but neither depends on the
other, so they aren't parallel-safe — drawn dashed + listed). Clicking or
focusing a node selects that phase everywhere (see pd-stepper). Place it in the
Plan tab; it replaces hand-drawn sequence diagrams.

```html
<pd-dag caption="Execution order"></pd-dag>
```

### <pd-trace caption>
Traceability matrix, fully derived from pd-ac. Renders an AC × phase × test
grid from each card's phases and tests attributes; rows missing a phase or a
test are flagged as coverage gaps. No authoring — it reads data already on the
pd-ac cards. Place it in the criteria section.

```html
<pd-trace caption="Acceptance coverage"></pd-trace>
```

### <pd-collapse summary>
Ad-hoc disclosure wrapper. Collapsed by default (add `open` to expand); the
summary is the scan line, the body stays in the DOM for agents. Use for long
code, tables, or secondary rationale that isn't a whole section.

```html
<pd-collapse summary="Why token bucket (rationale)">
  <md><script type="text/plain">…three paragraphs…</script></md>
</pd-collapse>
```

Note — automatic Plan-tab file mirror: when a pd-files tree lives on a
different tab from the phase controls (the usual Solution → Plan split), a
synced read-only copy is auto-injected next to the pd-dag/pd-stepper so the
click-through is visible in one place. Nothing to author.

### <pd-decisions title>
Auto-generated decision log: lists every resolved/rejected thread in the doc
with its outcome. Place once, usually in the first tab. No children needed.

```html
<pd-decisions></pd-decisions>
```

### <pd-wire label h> / <pd-note>
Wireframe primitives for mockup sections. pd-wire is a labeled placeholder box
(h = min-height, e.g. "8rem"); pd-note is an annotation callout. Combine with
freeform Tailwind HTML for layout (grids, flex rows).

```html
<div class="grid grid-cols-3 gap-2">
  <pd-wire label="Nav" h="14rem"></pd-wire>
  <div class="col-span-2">
    <pd-wire label="Settings form" h="10rem"></pd-wire>
    <pd-wire label="Save / Cancel" h="3rem"></pd-wire>
  </div>
</div>
<pd-note>Form fields mirror the team config schema; nav reuses the app shell.</pd-note>
```

## Merging reviewer comments

Reviewers queue comments in the browser and paste an export block to you.
The block contains inline instructions — follow them exactly. Example:

```
=== DOC COMMENTS ===
doc: 021: API rate limiting

INSTRUCTIONS — you MUST follow these steps in order:
1. Merge every comment below into the HTML doc file FIRST, before responding.
   - REPLY → append <pd-comment by="review">…</pd-comment> to the named thread.
   - NEW → create a <pd-thread anchor="…" priority="…" title="…"> after the anchored element, containing the comment.
2. Then respond to each comment in the same thread (append your own <pd-comment by="author">).
   Set status="resolved" when addressed, or "rejected" with reasoning. Never edit or delete existing comments.

[1] REPLY to thread "Why not sliding window?" (anchor: approach)
    Fine, but document the burst size limit.
[2] NEW p1 comment on "Files" (anchor: files)
    The limiter must also cover the websocket gateway.
=== END DOC COMMENTS ===
```

After merging, tell the user; their browser copy clears pending comments via
the Clear button (localStorage — a reload after your edit shows merged state).
